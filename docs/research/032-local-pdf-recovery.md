## 0. 결론

1. **폼 입력란 전용 PDF는 OCR 없이 정확한 값 그대로 복원된다.** pdf.js 6.4.299의 `getAnnotations()`가 4개 위젯의 값 527자(눈에 보이는 글자 396자)를 읽었고, 이는 PyMuPDF가 읽는 값과 글자 종류별 개수까지 같다. **같은 값을 앱의 PDFium(WASM)으로도 읽을 수 있다**: wasm이 `FPDFAnnot_GetFormFieldValue` 등을 내보내고, 20줄짜리 패치 워커로 11ms 만에 읽었다(✅ 실행). plan 011의 "웹에서 폼 값을 읽는 API 없음"은 **pdfrx의 Dart API에 한해서만** 맞고 엔진에는 해당하지 않는다.
2. **스캔·이미지·도형 글자 PDF는 브라우저 로컬 OCR(Tesseract.js 7.0.0, 한국어+영어)로 실용 수준까지 읽힌다.** 단 **기본 설정으로는 안 된다**(이전 Node 결과를 브라우저에서도 그대로 재현: 쪽당 CER 10~16%, 표 셀 재현 19%). 아래 "레시피"를 쓰면 같은 이미지에서 **양호한 스캔 8장 기준 CER 3.0%, 단어 재현율 97%, 표 셀 93%, 숫자·날짜 99%**. 화질이 나쁘면(100dpi+노이즈+기울기) 단어 재현율 약 74%, 60dpi는 약 51%로 떨어진다.
3. **유료 비전은 정확도에서 여전히 우위**(같은 이미지에서 CER 0~0.46%)지만, 로컬 경로가 **양호한 스캔에서는 검색에 쓸 만큼** 따라온다. 그래서 **주 경로 = 폼 값(pdf.js 또는 패치 PDFium) → 로컬 OCR, 유료 비전 = 사용자가 동의할 때만 쓰는 품질 향상 옵션**을 추천한다.
4. **ADR 003은 그대로 유지**된다(서버는 텍스트만 받는다). 서버 비용·남용 위험(031의 P3)·프라이버시 예외(031의 P2)가 사라진다. 대신 **클라이언트 부담**(첫 사용 시 약 4~7MB 지연 로드, 쪽당 0.5~3.5초, 메모리)이 생긴다.
5. **미해결 한계(⚠️)**: 실제 스캔 파일 미평가(전부 합성), 한국어 단어 사이 **잘못된 공백**(Tesseract 특성), 다단·테두리 없는 표는 휴리스틱으로만 처리, 저사양 모바일 성능 미측정.

추가로 정의한 지표(검색 관점):

- **단어 재현율(공백 무시)**: 정답 토큰(2자 이상)이 OCR 출력에서 **공백을 모두 지운 문자열의 부분 문자열로** 나타나는 비율. Tesseract가 한글 단어 안에 공백을 끼워 넣어(§3.6) 엄격한 단어 일치는 과소평가되므로 이 지표를 주로 쓴다. 엄격 일치도 함께 적는다.
- **숫자·날짜 재현율**: 정답의 2자 이상 숫자열(`48,000`, `09:30`, `051 555 0142` 등)이 그대로 남는 비율.

## 2. 폼 입력란 PDF (사용자 샘플 `부산 여행 계획.pdf`)

### 2.1 구조 (글자 수·구조만)

| 항목 | 값 |
|---|---|
| 쪽 | 1쪽, 회전 270°, MediaBox 595×842 |
| AcroForm | 있음, 위젯 4개 모두 텍스트 필드(`Tx`), 그중 멀티라인 2개 |
| 값(`/V`) 길이 | 11 / 257 / 5 / 254 = **527자** (공백·줄바꿈 131자 포함, 눈에 보이는 글자 396자) |
| 본문 텍스트 | 0자 (pdf.js `getTextContent` 0, PDFium 0 ✅) |
| 필드 이름 | 영문 식별자 10~15자, 설명(툴팁) 없음. 이름이 뜻을 담는지는 ⚠️ 미확인(내용을 출력하지 않음) |
| 상자 배치 | 4개 중 일부가 겹쳐 있음(작은 필드가 큰 필드 영역 안에 놓임) → 좌표 정렬 읽기 순서가 모호 |

### 2.2 "537자 근처가 복원되는가" — 해소

PyMuPDF `get_text()`의 **537자**와 값 합계 **527자**는 숫자가 달라 보이지만 같은 내용이다. 문자 종류별로 비교했다(내용 출력 없음).

| 종류 | 값 `/V` (527자) | PyMuPDF `get_text` (538자 중) |
|---|---|---|
| 한글 | 316 | 316 |
| 구두점 | 31 | 31 |
| 숫자 | 38 | 38 |
| 라틴 | 9 | 9 |
| 기호 | 2 | 2 |
| 공백·줄바꿈 | 131 | 27 + **제어문자 115** (공백을 제어 코드로 표현) |

→ **눈에 보이는 글자 396자는 완전히 같고**, 537↔527 차이는 PyMuPDF가 공백을 제어문자로 내보낸 표현 차이뿐이다(외형 텍스트 스트림에 `/V`에 없는 글자가 따로 있지 않음). 따라서 `/V` 경로가 손실 없는 정답 소스다. (✅ 확인)

### 2.3 방법 A — pdf.js (브라우저에서 실행 ✅)

| 항목 | 결과 |
|---|---|
| API | `getDocument({data})` → `page.getAnnotations()` → `subtype === 'Widget'`의 `fieldType`, `fieldValue`, `multiLine`, `rect` |
| 사용자 샘플 | 위젯 4개, 값 길이 11/257/5/254 = PyMuPDF와 일치, 문서 열기부터 값 읽기까지 **48ms** |
| `getFieldObjects()` | **0개를 반환**(사용자 샘플·합성 샘플 모두) → 구현은 `getAnnotations()`를 써야 한다 |
| 값 형식 | 텍스트 필드: 문자열(줄바꿈 `\n` 포함). 체크박스: `"Yes"`. 콤보박스: **배열** `["Busan"]` → plan 011의 R-4(문자열이 아닐 수 있음)가 실제로 발생 ✅ |
| 쪽 소속 | `getAnnotations()`를 호출한 쪽 번호가 곧 소속 쪽. 합성 3쪽 PDF에서 1쪽 4개·2쪽 1개·3쪽 0개 정확 ✅ (plan 011 R-3 해소) |
| 순서 | 기본은 주석 배열 순서. 회전·겹침 때문에 좌표 정렬은 이 샘플에서 모호 ⚠️(읽기 순서 품질 미평가) |
| 라벨 | 필드 이름만 있고 뜻이 불명확 → **값만 쓰고 이름은 쓰지 않기를 권장**. 선택적으로 합성 샘플처럼 이름이 의미 있을 때만 접두 |
| 번들 | `pdf.min.mjs` 0.44MB(gzip 0.13) + `pdf.worker.min.mjs` 1.21MB(gzip 0.36). 폼 값만 읽으려면 `wasm/`(jbig2·openjpeg·qcms·quickjs) 불필요 ✅ (스캔·표준 폰트 경고는 무시 가능, 값 읽기에 영향 없음) |

### 2.4 방법 B — 앱의 PDFium(WASM)에서 직접 읽기 (✅ 실행)

| 질문 | 확인 |
|---|---|
| pdfrx Dart API에 폼 값 읽기가 있나 | **없다.** `PdfAnnotation`은 링크 주석 메타(제목·내용·날짜)뿐이고, `loadLinks`만 `FPDFAnnot_GetStringValue`를 쓴다 |
| pdfium.wasm이 폼 함수를 내보내나 | **내보낸다.** `FPDFAnnot_GetFormFieldName/Type/Value/AlternateName`, `FPDFAnnot_GetSubtype/GetRect`, `FPDFPage_GetAnnot*`, `FPDFDOC_InitFormFillEnvironment` 등(총 482개 export). 반면 `FPDFPage_Flatten`은 **없다**, OCR 관련 export도 **없다** |
| 폼 환경은 이미 초기화되나 | 그렇다. 워커 `_loadDocument`가 `FPDFDOC_InitFormFillEnvironment`를 호출하고 `formHandle`을 반환한다 |
| 워커가 노출하나 | **아니다.** 명령 표(`functions`)는 `loadDocumentFromData, loadPage, renderPage, loadText, loadLinks, …` 18개뿐이고 폼 읽기 명령이 없다 |
| 패치로 읽어지나 | **읽힌다.** 워커에 `readFormFields` 명령 20줄을 추가하고(`FPDF_LoadPage` → `FPDFPage_GetAnnot` → 위젯(subtype 20)이면 `FPDFAnnot_GetFormFieldType/Name/Value`, `GetRect`), 페이지에서 `PdfiumWasmCommunicator.sendCommand`로 호출 |
| 결과 | 사용자 샘플 4개 위젯, 값 길이 **11/257/5/254**(pdf.js와 동일), 유형 6(텍스트), 소요 **11ms**. 합성 샘플은 텍스트·체크박스(유형 2, `Yes`)·콤보박스(유형 4, `Busan`) 값과 쪽 소속이 정확 |
| 앱에 넣는 방법 | `Pdfrx.pdfiumWasmModulesUrl`(또는 `<meta name="pdfium-wasm-module-url">`)로 **자체 호스팅한 패치 `pdfium_worker.js`**를 가리키고, Dart에서 `dart:js_interop`로 `PdfiumWasmCommunicator.sendCommand('readFormFields', …)`를 호출(문서 핸들은 별도로 `loadDocumentFromData` 명령으로 열어 얻음). pdfrx Dart 패키지를 포크하지 않아도 된다 |
| 비용 | 번들 증가 0, 코드 약 20줄(JS) + 약 60줄(Dart 호출). **단 pdfrx를 올릴 때마다 워커를 다시 패치·검증해야 하는 유지 부담**(워커는 pdfrx 버전에 종속) ⚠️ |

**비교와 권장**: pdf.js는 +0.5MB(gzip) 지연 로드·표준 API·업그레이드 부담 없음(단, 값만 읽는 용도에 두 번째 PDF 파서를 싣는 셈). 패치 PDFium은 번들 0이지만 pdfrx 업그레이드마다 점검. **폼 PDF는 드물어(plan 011이 P3로 분류) 유지 부담이 적은 pdf.js(지연 로드)를 1순위**로, 패치 PDFium은 "번들을 줄여야 할 때의 대안"으로 둔다. (결정 사항 D2)

### 2.5 pdfrx 렌더가 폼 값을 그리는가 → OCR 입력으로 쓸 수 있는가 (✅ 실행, [research 031](031-pdf-without-text.md) §M2 ⚠️ 해소)

| 렌더 모드 | 사용자 샘플 1쪽(1684×1190) 비흰색 픽셀 |
|---|---|
| `none` | 0 |
| `annotation` | 0 |
| **`annotationAndForms`(pdfrx 기본값)** | **65,840** (폼 값이 그려짐) |

- 합성 폼도 같은 결과(1쪽 2,961 → 11,227px, 2쪽 0 → 1,568px). 즉 **기본 `page.render()`가 입력란 글자를 그린다** → 앱이 이미 쓰는 렌더 그대로 OCR 입력이 된다.
- 그 렌더를 로컬 OCR(§3의 레시피)에 넣은 결과: 정답(pdf.js 값) 대비 **CER 9.8%, 토큰 재현 118/126(94%)**, OCR 0.91초(쪽 1754×1239). `none` 모드는 0자.
- 그러나 **외형(appearance)에 글리프가 없으면 렌더→OCR은 실패한다**: 합성 한글 폼은 외형 폰트(Helv)에 한글 글리프가 없어 렌더에 숫자만 보였다(`2 3 480, 000`). 이는 PyMuPDF 생성기의 한계이지 OCR 결함이 아니지만, **현실에서도 "렌더에 안 그려지는 폼"이 있으면 `/V` 경로만 값을 읽는다**는 점이 중요하다. → **폼 값 추출을 OCR보다 먼저 시도해야 한다**(§5).

## 3. 브라우저 로컬 OCR (Tesseract.js 7.0.0)

### 3.1 호스팅·번들·언어 데이터 크기 (✅ 실측)

| 파일 | 원본 | gzip | brotli |
|---|---|---|---|
| `tesseract.min.js` | 0.06MB | 0.01 | 0.01 |
| `worker.min.js` | 0.11MB | 0.03 | 0.03 |
| 코어 `tesseract-core-*-lstm.wasm.js` (simd / relaxedsimd / 일반 각각 3.72MB, **클라이언트는 1개만 받음**) | 3.72MB | 1.39 | 1.21 |
| `kor` fast | 1.60MB | 1.05 | 1.03 |
| `eng` fast | 3.92MB | 1.87 | 1.72 |
| `kor` best_int (tesseract.js 기본) | 2.11MB | 1.49 | 1.47 |
| `eng` best_int | 4.96MB | 2.80 | 2.64 |
| `kor` best (float) | 11.95MB | 11.02 | 11.00 |
| `eng` best (float) | 14.69MB | 12.20 | 12.05 |
| `kor`/`eng` 4.0.0 기본(레거시 포함) | 14.61 / 22.38MB | 6.68 / 10.30 | 6.02 / 9.07 |
| (참고) 앱이 이미 싣는 `pdfium.wasm` | 4.99MB | 2.29 | 2.06 |

- **fast 한국어+영어 + 코어 + 워커 = 약 4.2MB(gzip 기준 전송량)**, 압축이 없으면 코어 3.72MB + 언어 데이터 `.gz`(tesseract.js가 직접 gunzip, 한국어 1.05 + 영어 1.87MB) ≈ **6.7MB**.
- **tessdata_best(float) 모델은 tesseract.js 7.0.0 브라우저 SIMD 코어에서 동작하지 않는다**: `Aborted(missing function: _ZN9tesseract13DotProductSSEEPKfS1_i)`. `legacyCore: true`로도 같은 오류, SIMD 없는 일반 코어를 강제하면 동작(정확도는 best_int와 ±1%p 이내, 쪽당 3.7~7.3초로 느림) → 실사용 불가(✅ 실측).
- **성능 코어 선택**: relaxedsimd = simd(같은 속도), **SIMD 없는 코어는 2배 느림**(희소한 쪽 0.86s → 1.74s, 촘촘한 쪽 3.5s → 9.3s). Chrome은 `relaxedsimd-lstm`을 선택했다. `corePath`는 **여러 파일이 모두 있는 디렉터리**여야 하므로 배포에는 lstm 코어 3개(11.2MB 원본)를 놓아야 한다(클라이언트는 1개만 받음) ⚠️ 다른 브라우저의 선택은 미확인.

### 3.2 첫 로드·캐시 (✅ 실측, 서버가 gzip/br로 응답하는 로컬 서버 + 대역폭 제한)

| 조건 | 첫 사용(빈 캐시) 초기화 | 재방문(언어 데이터 IndexedDB 캐시 + HTTP 캐시) |
|---|---|---|
| 제한 없음(로컬) | 0.28초 | 0.15초 |
| 20Mbps | **1.4초**(전송 4.17MB) | 0.6초(*) |
| 5Mbps | **5.2초** | 2.3초(*) |
| best_int, 20Mbps | 1.8초(전송 5.52MB) | 0.6초(*) |

(*) 이 측정 서버가 `ETag`/`Cache-Control`을 보내지 않아 **코어 1.4MB를 다시 받았다**. 언어 데이터는 IndexedDB에서 읽혀 재다운로드되지 않았다. 적절한 캐시 헤더가 있으면 재방문 전송량은 거의 0.
- 첫 recognize까지 포함하면 +0.8~1.1초(첫 쪽 처리). 인터넷 속도가 낮은 환경(5Mbps 이하)에서는 **첫 사용 시 5초 이상**이므로 진행 표시가 필요하다.
- 로컬 서버 측정이므로 **실제 Serverpod Cloud에서의 전송 시간은 ⚠️ 미측정**이다.

### 3.4 정확도: 기본값 → 레시피 (✅ 실측, 합성 스캔)

합성 샘플: A1(문단+영어+표+목록)·B1·B2(주입 문장 포함) 정답으로 11개 이미지(깨끗한 150/200dpi, 실제 같은 200dpi 스캔 3, 나쁜 100dpi 노이즈·기울기 3, 이전 110dpi JPEG q45 2, 60dpi 1). 전부 **한 글꼴·한 단 구성**이라 일반화는 §3.8을 본다.

**시도한 변수와 결과** (단어 재현율 평균 기준, 각 변수는 다른 것을 고정하고 비교):

| 변수 | 결과 |
|---|---|
| **PSM** | **PSM 6(tesseract.js 기본)은 표를 망가뜨림**(표 셀 재현 9~25%). **PSM 4(단일 열)가 최고**(표 셀 77~83%, 문단 87~90%). PSM 3은 중간. PSM 11은 순서가 흩어짐 |
| 언어 데이터 | fast ≈ best_int ≈ best(float) ≈ 4.0.0: 평균 단어 재현 84.4 / 85.0 / 85.5 / 84.3%(차이는 잡음 수준). **fast를 추천**(가장 작고 빠름). `kor` 단독은 영어·한글 모두 나빠짐(61→42%), 언어 순서(`kor+eng` vs `eng+kor`)는 영향 없음 |
| 해상도 | **100~250dpi는 비슷**(CER 2.1~2.9%), **300dpi(2480×3509)는 급락**(CER 9%, 표 셀 48%). 업스케일(1.5×, 2×)은 오히려 악화(표 셀 82% → 41%). → **A4 기준 약 150dpi(긴 변 1,750px)로 렌더** |
| 이진화(오츠)·대비 확장·블러·적응형 임계 | 모두 **악화**(77~78%, 적응형 43~47%) |
| `preserve_interword_spaces`, `user_defined_dpi` | 무의미/미세 |
| 표 테두리 제거(직접 구현) | 악화(66%). 표 문제는 테두리가 아니라 **PSM 6 때문**이었다 |
| **배경 평탄화**(국소 최대값으로 나눔) | 조명 불균일·노이즈 스캔에서 **크게 개선**(나쁜 100dpi: 단어 재현 ~20% → 62%). 평탄화 없이는 나쁜 스캔이 사실상 실패 |
| **기울기 보정**(투영 프로파일, ±4°) | 추정값은 실제 기울기와 일치(0.75°, 2°, 2.5°, 1.25°). **2°급 기울기에서 효과 큼**(나쁜 100dpi + 평탄화: 45/71/71 → 74/75/72%), **0.75° 이하는 보정하면 오히려 악화**(재샘플링 번짐: 99%→89~90%) → **|각도| ≥ 1°일 때만 회전** |
| Sauvola(`thresholding_method=2`) | 평탄화+보정과 비슷(82.9 vs 84.0%), 코드 불필요한 대안. 양호한 스캔에서는 약간 낮음 |
| 정정 기록 | 측정 도중 회전 시 캔버스 모서리가 **검게 남는 버그**(회전된 흰 배경)를 발견했고, 이 때문에 초기의 "기울기 보정 효과"가 과대였다. 수정 후 **모든 수치를 다시 쟀고** 위 표는 수정판이다(`res/final_blackwedge.json`은 폐기용 보관) |

**최종 레시피(F)**: `fast` 한국어+영어, PSM 4, A4 약 150dpi 렌더, 그레이스케일, **배경 평탄화**, **기울기가 1° 이상일 때만 보정**, (다단이면 영역 분할 §3.8). 이진화·업스케일 없음.

### 3.6 Tesseract의 한국어 단어 공백 문제 (✅ 실측, 중요 한계)

출력에 한글 음절 사이 **불필요한 공백**이 낀다: `이번 워 크 숍 은 2026 년 11 월 14 일`, `오 세 린`, `점심 도 시 락 이 포 함 됩니다.`(CER·공백무시 재현율은 정상). 이 합성 글꼴(AppleGothic)의 자간 영향일 수 있고, **실제 한국어 문서(맑은 고딕·바탕 등)에서 정도는 ⚠️ 미평가**.

| 지표 | 양호한 스캔 평균 |
|---|---|
| 공백 무시 단어 재현 | 97% |
| **엄격(공백 유지) 단어 재현** | **75%** (레시피 F 출력으로 재집계 75.3%) |
| 단어 박스 간격으로 공백 복원(간격 < 줄높이×0.2면 붙임) | 83% (레시피 F 출력 83.3%, 같은 데이터에서 정한 값이라 낙관적 ⚠️) |

영향: 임베딩·LLM은 이 정도 공백을 견디지만 **정확 일치 검색(키워드)과 인용 하이라이트의 문자열 매칭**은 약해진다. 완화: ① 줄 단위 텍스트와 **줄·단어 상자 좌표**를 함께 저장해 쪽 이미지 위 하이라이트로 인용을 표시(텍스트 매칭 불필요), ② 저장 시 `squash`된 변형을 키워드 색인에만 추가. 둘 다 ⚠️ 미구현.

### 3.7 줄 단위 텍스트·하이라이트

Tesseract는 줄·단어 상자(`bbox`)를 돌려준다(줄마다 `[x0,y0,x1,y1]`와 단어별 상자, 블록→문단→줄→단어 구조). 앱의 인용 하이라이트(U2)가 줄/문장 단위 텍스트를 쓰므로 **OCR 쪽은 줄 단위로 청크화**하면 되고, PDFium `loadStructuredText`의 글자 상자가 없는 대신 OCR 상자를 이미지 좌표로 환산해 같은 하이라이트 UI를 쓸 수 있다 ⚠️ 미구현·미검증.

### 3.8 일반화 점검 (정직한 한계)

레시피는 한 글꼴·한 단 3개 레이아웃에서 약 30개 설정을 고르며 정했으므로 **표본 내(in-sample)** 수치다. 별도 검증을 했다.

| 검증 | 결과 |
|---|---|
| **다단 쪽**(2단, 9.5pt, 제목+본문 2블록; 새 문장) | PSM 4: 단락 CER **56~57%**(줄이 단을 가로질러 합쳐짐, 합쳐진 줄 11/12). PSM 3: 깨끗한 쪽 2.4%지만 단일 단 촘촘한 쪽은 **15.8%**(PSM 4는 4.9%) → 한 모드로 둘 다 못 푼다 |
| **간단한 열 분할(XY-cut: 가로 빈 줄로 띠 분할 → 띠 안에서 세로 빈 열 찾기, 표 테두리 제거, 열 폭≥30%·줄 채움≥0.55 조건) → 영역별 PSM 4** | 다단 쪽 CER **2.0%**(깨끗), **1.2%**(스캔), 11개 단일 단 쪽 **오분할 0건**(결과 동일), 단 촘촘한 쪽 4.9%·영역 1개 |
| **보류(held-out) 다단 쪽**(10.5pt, 다른 간격·문장; 분할기는 이 쪽을 평가하기 전에 확정. 단 첫 시도 쪽은 열 사이 간격이 없는 결함 있는 생성물이라 폐기했고, 그 쪽을 보고 `gx`를 0.02→0.012로 낮췄다) | PSM 4: 63%(깨끗)·64%(스캔), PSM 3: 63%·0.0%. **분할기: 2.1%(깨끗), 0.0%(스캔)** ✅ (표본 1쪽) |
| **테두리 없는 키·값 표**(분할되면 안 됨) | 분할 안 됨(올바름). 행 연결: PSM 4 깨끗 7/8 · 스캔 4/8, PSM 3 깨끗 0/8 · 스캔 7/8 → **모드에 따라 흔들림** ⚠️ |

한계: 열 분할 임계값(`gy` 2.2→1.5×줄높이, 노이즈 허용 행 수, 열 폭·채움 조건)은 첫 다단 쪽 2장(깨끗·스캔)을 보며 조정했고, 두 번째 레이아웃 1쪽에서 통과했다(표본이 매우 작음). 3단·혼합 레이아웃·사선 단·표 안의 단은 미검증 ⚠️. 열 분할이 실패하면 **조용히 줄이 뒤섞인 텍스트**가 나오므로 "OCR 오류 가능" 라벨과 쪽 신뢰도 표시가 필요하다.

## 4. 외부 서비스(OpenRouter `file-parser`) — 로컬 경로가 아님

공식 문서 `https://openrouter.ai/docs/guides/overview/multimodal/pdfs`(마크다운 원문 `…/pdfs.md`를 직접 읽음 ✅):

- 엔진: `cloudflare-ai` — "Converts PDFs to markdown using Cloudflare Workers AI (**Free**)"; `mistral-ocr` — "**Best for scanned documents or PDFs with images** ($2 per 1,000 pages)", 미국 리전 고정 시 $2.2; `native` — 모델이 파일 입력을 지원할 때만, 입력 토큰으로 과금. `pdf-text`는 deprecated → `cloudflare-ai`로 리다이렉트.
- **`cloudflare-ai`가 스캔(이미지) PDF를 OCR하는지는 문서에 쓰여 있지 않다**(스캔용으로 지정된 엔진은 `mistral-ocr`). 따라서 "무료 엔진으로 스캔도 읽힌다"고 가정하면 안 된다 ⚠️(실제 호출은 금지 규칙으로 하지 않음).
- 엔진 미지정 시 모델이 파일을 직접 받으면 `native`, 아니면 `mistral-ocr`. OCR 요금은 BYOK여도 OpenRouter 계정에 청구. `mistral-ocr`은 PDF당 이미지 최대 8개.
- 어느 엔진이든 **PDF가 외부(OpenRouter 및 하위 처리 서비스)로 전송**되므로 이 설계의 "외부 전송 0" 경로가 아니다. (이전 조사의 mistral-ocr 쪽 구분 없음·쪽당 $0.0024는 design-031에서 실측.)

## 5. 하이브리드 설계

### 5.1 흐름

```text
업로드/드롭
 └ extractPages(bytes)                         # 기존: pdfrx loadStructuredText
    └ 쪽별 "눈에 보이는 글자 수" 계산 (공백·제어문자 제외)
       ├ 모든 쪽 ≥ 30자 ──────────────────▶ 기존 흐름 (아무것도 안 함, pdf.js/OCR 코드는 내려받지 않음)
       └ 30자 미만 쪽 k개 (T1~T5)
          (a) 폼 값 추출: 패치 PDFium 또는 pdf.js(지연 로드) → 그 쪽의 텍스트 필드 값
              성공(≥ 10자)하면 source='form'으로 채움 (무료·정확·즉시)
          (b) 남은 빈 쪽: 로컬 OCR
              - 안내 시트: "글자로 선택되지 않는 쪽 n개를 이 기기에서 읽어요(외부로 전송하지 않아요). 약 {sec}초"
              - OCR 코드·언어 데이터를 지연 로드(4~7MB) → 진행 "글자를 읽는 중 i/n쪽" (취소 가능)
              - 쪽 렌더(≈150dpi) → 전처리(평탄화·기울기·영역) → Tesseract(워커) → 줄 단위 텍스트
              - 결과를 source='ocr'로 DocPage에 채움
          (c) 라벨: "OCR로 읽은 내용 · 오류가 있을 수 있어요" (카드 칩, 뷰어 배너, Ask 출처 칩)
          (d) 의심 쪽(쪽 신뢰도가 낮거나 글자 수가 비정상적으로 적음): "읽기 어려운 쪽이 있어요 [AI로 다시 읽기(외부 전송)]" ← 선택 옵션(후속). 신뢰도 단독 판정은 약하므로(§3.5) 사용자가 쪽을 직접 고르게 하는 것을 기본으로
       └ 업로드는 기존 `upload(...)`와 같은 서버 API (서버는 텍스트만 받음)
```

- 감지 단위는 **문서가 아니라 쪽**(031의 P4 그대로): 혼합 PDF(T2), 푸터만 있는 스캔(T3)도 쪽별 30자 임계로 잡힌다. 합성 `mixed.pdf`에서 쪽별 글자 수 `[51, 0]`을 정확히 구분했고 0자 쪽만 OCR하면 되며, 글자가 **도형**인 PDF(T5)도 PDFium 0자 → OCR로 정확히 읽었다(합성 `text_as_outline.pdf` ✅).
- 순서 이유: 폼 값은 **정확**하고 (렌더에 안 그려지는 폼도 읽음) 비용이 거의 없다. 그래서 OCR보다 먼저.

### 5.2 클라이언트 구현 요건 (측정에서 나온 것)

1. **문서를 한 번 열고 쪽만 렌더**한다(`PdfDocument`를 재사용). BGRA→RGBA 변환·전처리는 **메인 스레드 밖(Web Worker/OffscreenCanvas)** 에서 한다(메인 스레드 전처리가 쪽당 45~100ms).
2. **순차 처리, 동시 1쪽**(워커 1개). 병렬은 메모리만 늘리고 이득이 작다(⚠️ 미측정).
3. **취소**: 진행 시트의 취소 → `worker.terminate()`로 즉시 메모리 회수, 이미 읽은 쪽은 버리지 않고 "읽은 쪽만 올리기/버리기" 선택.
4. **진행 표시**: 첫 사용 시 "엔진 내려받는 중(약 4~7MB)"과 "i/n쪽" 두 단계. 기존 `upload_tray`의 쪽 n/m 행을 재사용.
5. **실패 처리**: 엔진 로드 실패(오프라인 등)·쪽 렌더 실패·쪽 OCR 0자 → 쪽 단위로 기록하고 읽은 쪽만 `ready`, 실패 쪽은 [다시 시도]. 전부 0자면 기존 `no_text` 안내로 귀결(앱은 죽지 않음, plan 011의 A-6과 같은 원칙).
6. **쪽 상한**: 문서당 OCR 쪽 상한(제안 50, 설정 상수) — 쪽 수×0.5~3.5초 + 저사양 모바일 위험 때문. 초과 시 "앞 50쪽만 읽을까요?".
7. **후처리**: 줄 단위로 정리, 코드펜스·`|` 같은 마크다운 잔여 없음(Tesseract는 평문), 보이는 글자 10자 미만이면 빈 쪽으로 기록(031의 `cleanTranscript` 규칙 재사용).
8. **쪽 신뢰도**: 프로토타입 `recogRegions`는 신뢰도를 0으로 돌려준다. 구현 시 영역별 단어 신뢰도를 평균내어 쪽 신뢰도로 저장해야 의심 쪽 표시에 쓸 수 있다.
9. **메인 스레드 주의**: §3.3의 "프레임 간격 최대 33ms"는 Tesseract 워커 + 단순 전처리 시점의 측정이다. 권장 레시피의 전처리(평탄화·기울기·영역 분할)는 메인 스레드에서 쪽당 45~100ms이므로, **전처리를 워커/OffscreenCanvas로 옮겨야** 그 수준이 유지된다(위 1번).
10. **모바일 저사양 경고**(⚠️ 미측정): SIMD 없는 환경은 2배 느림. 쪽 상한을 더 낮추거나 "데스크톱에서 읽기" 안내.

### 5.3 스키마·서버 변경 (최소)

| 변경 | 내용 |
|---|---|
| `DocPage.source` (031의 제안 재사용) | 값을 `text`(기본) / `form` / `ocr` / (후속) `ai`·`memo` 로 확장. 추가 컬럼 1개, 비파괴 마이그레이션 |
| `PageText.source` (nullable, 테이블 아님) | `_index`가 `DocPage.source`로 기록하고 `reindex`가 그대로 전달 → **재색인에서 라벨이 사라지지 않게 함**(031 P10과 같은 보호). `upload`가 기존 문서의 비-`text` 쪽을 빈 문자열로 덮지 않게 하는 규칙도 같이 |
| `Citation.source` (nullable) | Ask 출처 칩/뷰어 배너 라벨용(031의 §6.3과 동일) |

| ADR 003 | **그대로 유지**(PDF 파싱·OCR 모두 클라이언트, 서버는 텍스트만) |

- 서버 부담·남용 위험: **0**. 031의 `transcribePage`(이미지를 받아 유료 모델에 넘기는 열린 프록시), 쪽/일 한도, `aiReadEnabled`, `data_collection: deny`, 동의 UI, 크레딧 한도는 이 경로에서는 필요 없다. 이미지가 서버나 외부로 나가지 않으므로 **동의 시트가 정보 안내 한 줄로 단순**해진다.
- OCR 텍스트가 Ask의 근거로 들어가는 **프롬프트 주입 위험은 기존 PDF와 같은 수준**(OCR은 지시를 따르지 않음). 031의 D9(Ask `_system`에 주입 방지 문장 추가)는 여전히 독립 안건.

### 5.4 데모 계정

- 로컬 OCR은 서버 비용이 없으므로 031의 "데모 비활성"이 필요 없다. 데모에서도 **클라이언트 쪽 상한(예: 10쪽)** 만 두면 안전하고, 기존 `DemoGuard`(문서 5개·질문 50회/일)는 그대로 적용된다.
- 데모 시연용으로 미리 OCR한 스캔 샘플을 `SamplePack`에 `source='ocr'`로 넣어 두면 첫 로드 없이 라벨 UX를 보여줄 수 있다(031의 (a)와 동일).

## 6. 비교표

로컬 = 폼 값 + 브라우저 OCR(레시피 F). 정확도는 같은 합성 입력 기준이고 **합성이라 실제 스캔은 더 낮을 수 있다**(양쪽 공통 한계).

| | **로컬(폼 + OCR)** | 유료 비전(M2, gemini-3.1-flash-lite) | mistral-ocr (OpenRouter) |
|---|---|---|---|
| 폼 입력란 PDF | **정확한 원문(CER 0, 396자 일치)**, 렌더 못 해도 `/V`로 읽음 | 렌더에 그려져야 읽음(폼은 렌더에 그려짐 ✅), 환각·오자 가능 | 폼 처리 미확인 ⚠️ |
| 스캔 정확도(양호) | CER 2~3%, 단어 재현 97~99%, 숫자·날짜 99% | CER 0% | CER 0% (2쪽, 이어붙음) |
| 표(셀 텍스트) | 양호한 스캔 93~100%(테두리 있는 표), 테두리 없는 표는 흔들림 ⚠️ | 마크다운 표로 0% | 마크다운 |
| 저화질(60~100dpi, 노이즈·기울기) | 단어 51~74% | 60dpi 0.46% | 미측정 |
| 한국어 단어 공백 | **불필요한 공백 다수**(엄격 재현 75%) | 문제 없음 | 문제 없음 |
| 줄·단어 좌표 | **있음**(하이라이트 가능) | 없음 | 없음 |
| 속도(쪽당) | 0.55~0.9초(희소), 약 3.5초(촘촘), 첫 사용 +1.4~5초(로드) | 1.6~2.2초 | 쪽 구분 없이 일괄 4.8초(2쪽) |
| 비용 | **0** | 쪽당 약 $0.0007 | 쪽당 약 $0.0024 ($2/1,000쪽 + 모델) |
| 프라이버시 | **기기 밖으로 안 나감** | 쪽 이미지가 OpenRouter→Google로 | 파일 전체가 외부로 |

## 9. ⚠️ 미확인

- **실제 스캔**(스캐너·휴대폰 촬영·팩스·손글씨·도장·세로쓰기·작은 글자) 정확도. 전부 합성이며 한 글꼴(AppleGothic)·한 단 3개 레이아웃에서 설정을 정했다.
- **한국어 단어 공백**이 실제 문서 글꼴에서 얼마나 나오는지.
- **저사양/모바일**(CPU 느림·SIMD 없음·메모리 한계) 성능, 다른 브라우저(Safari·Firefox)의 코어 선택과 동작.
- Serverpod Cloud에서의 **실제 전송 시간·압축·캐시 헤더**(로컬 서버로만 측정).
- 20쪽 시간은 쪽당 값에서 계산한 추정.
- 열 분할·표 처리 휴리스틱의 3단·혼합·테두리 없는 표 일반화.
- pdf.js 폼 읽기에서 **리치 텍스트(`/RV`)·서식 필드·XFA** 같은 특이 폼, 그리고 폼 쪽 읽기 순서 품질(겹친 상자).
- 패치 PDFium 워커의 pdfrx 업그레이드 호환 비용.
- 쪽 신뢰도로 "AI로 다시 읽기"를 자동 제안할 수 있는지(양호·나쁨 범위가 겹침, n=11).
- PSM 3/4 선택을 자동화하는 더 나은 방법(레이아웃 엔진), 줄·단어 상자 하이라이트의 실제 정합.
- OpenRouter `cloudflare-ai`가 스캔을 읽는지(문서에 없음, 호출하지 않음).
